# Post-merge audit — PRs #39–#43

**Created:** 2026-08-10
**Status:** Open — findings recorded, no fixes started
**Baseline:** `0a59c3d` → `99b9aa3` (HEAD at audit time)
**Scope:** Retrospective audit of the five merged PRs in that range: upstream
`(chibi test)` adoption + continuation refactor (#39), scaffold removal (#40),
SRFI 151/143/132 bundling with reference-suite validation (#41), Track Q PRD
(#42), and the both-backends test parametrization (#43).
**Method:** four parallel audits (continuation refactor, bitwise/fixnum stack,
Scheme libraries, test infrastructure), each diffing against the baseline and
verifying every claim by execution on **both** backends. Everything already
tracked in `TRACK_Q_QUALITY_PRD.md` (the six quarantined divergences, god
objects, missing fuzz/perf gates, doc drift) is excluded here.

Overall verdict: the architecture of what shipped is sound — the parametrized
test harness, the self-retiring divergence quarantine, the continuation
refactor, and the internal-library layering are good foundations. The debt is
concentrated in six confirmed library bugs, one latent GC soundness gap, and a
set of "trusted, not pinned" holes in the new verification machinery.

---

## The one-sentence lesson

**Every confirmed bug below sits in code that was locally adapted from an
upstream reference, at exactly the spot the upstream suite does not cover** —
the SRFI 132 RNG substitution (A1), the `bitwise-eqv` n-ary rewrite (A2), the
SRFI 60 aliasing (A3), the carry-op rounding (A4), the `copy-bit-field`
signature (A5). PR #41's thesis was "validate each bundled library against its
own reference suite"; that gate is blind precisely where we deviate from the
reference.

**Rule going forward:** every local deviation from an upstream source gets
(a) an in-file marker at the edit site, and (b) a local test that exercises the
deviation. E1 below makes the existing files conform.

## A — Confirmed library bugs

All six verified by execution on both backends. Ordinary bug fixes, not track
work; suggested as one PR (A1–A5) plus one small PR for A6. Each fix must add a
regression test **at the adaptation point** (see the lesson above).

### A1 `[x]` (#45) HIGH — SRFI 132 `vector-select!` / `vector-find-median` crash on ranges ≥ 50
`lib/srfi/132/select.scm:235-237` — upstream's SRFI-27 `random-integer` was
replaced by a hand-rolled LCG calling `fxand`, `fxwrap+`, `fxwrap*`,
`fxremainder`. None is bound: `(srfi 132)` imports only `(scheme base)`
(`lib/srfi/132.sld`), and `fxwrap+`/`fxwrap*` are Gambit-only names that exist
nowhere in this repo. Triggered whenever the range ≥ `just-sort-it-threshold`
= 50 (`select.scm:101`); reproduced with `(vector-select! < v 50)` on a
100-element vector, both backends. Masked because the reference suite never
exceeds ~12 elements.
**Fix sketch:** either import the needed ops or use a plain
fixnum-arithmetic LCG in `(scheme base)` terms; add a ≥ 50-element
`vector-select!`/`vector-find-median` regression test.

### A2 `[x]` (#45) HIGH — `bitwise-eqv` wrong for every even argument count
`lib/srfi/151/bitwise.scm:10-11` — `(bitwise-not (apply bitwise-xor -1 args))`
double-complements: `(bitwise-eqv 37 12)` → `41` (spec: `-42`); `(bitwise-eqv)`
→ `0` (spec identity: `-1`). Odd arities coincidentally agree, which is why
spot checks pass. Exported by `(srfi 151)`, `(srfi 33)`, and
`(scheme bitwise)`; zero coverage in both the hand-written tests and the
vendored chibi suite.
**Fix sketch:** fold binary eqv per element as the reference implementation
does; add even-arity + zero-arity regression tests.

### A3 `[x]` (#45) HIGH — SRFI 60 `integer->list` / `list->integer` / `booleans->integer` bit order reversed
`lib/srfi/60.sld:38-48` — aliased to SRFI 151's `bits->list` family, which is
LSB-first; SRFI 60 is MSB-first (`(integer->list 6)` must be `(#t #t #f)`, we
return `(#f #t #t)`). SRFI 151 *renamed* these procedures specifically to
avoid this silent incompatibility. Compounding it,
`crates/patina-tests/tests/srfi_151_bitwise.rs:127-128` pins the wrong order
as expected — the suite currently enforces the bug. SRFI 60 is the
highest-in-degree library in the compat corpus (the headline motivation for
PR #41).
**Fix sketch:** implement the three procedures with reversal (or a direct
MSB-first loop) in a small `lib/srfi/60/` shim; flip the test expectations.

### A4 `[x]` (#45) HIGH — `fx+/carry` family returns a non-fixnum at the half-point boundary
`lib/srfi/143/fixnum.scm:44-47` — `balanced/` uses `(round (/ n d))`; R7RS
`round` is half-to-even, so a sum of exactly `2^(fx-width-1)` lands on the
excluded endpoint: `(fx+/carry fx-greatest 1 0)` → `(2^60 0)` with
`(fixnum? r)` = `#f`; correct is `(fx-least 1)`. Affects `fx+/carry`,
`fx-/carry`, `fx*/carry` — the operators that exist solely for this boundary.
Neither the hand-written test (off-boundary operands) nor chibi's 143 suite
(no carry assertions) reaches it.
**Fix sketch:** use floor-based balanced reduction (choose the representative
in `[fx-least, fx-greatest]` explicitly) instead of `round`; add the exact
half-point cases as regression tests.

### A5 `[x]` (#45) MEDIUM — SRFI 33 `copy-bit-field` uses the wrong signature
`lib/srfi/33.sld:31-34` — defined as `(to from start end)` (SRFI 60's
convention); SRFI 33 specifies `(size position from to)`, and chibi's own
`(srfi 33)` — from which the rest of the file is copied, including
`replace-bit-field (size position newfield n)` — implements size/position.
Spec-conforming callers get numerically wrong answers, not errors, and the
library is internally inconsistent about its own convention. Only 1 of the 5
SRFI-33-specific field ops is tested.
**Fix sketch:** match chibi's signature; cover all five field ops.

### A6 `[x]` (#46) MEDIUM — `(arithmetic-shift 1 (expt 2 40))` aborts the process
`crates/patina-primitives/src/primitives/bitwise.rs:96-100` — a fixnum shift
count flows unguarded into num-bigint's `<<`, which eagerly allocates
`count/64` words (~137 GB here): a Rust allocation abort, not a catchable
Scheme error. Inconsistent with the *bignum*-count path right above it
(`:91-93`), which raises a proper error. A Scheme-reachable interpreter kill.
**Fix sketch:** cap the accepted left-shift count (e.g. reject counts whose
result would exceed a sane bit-length) with the same catchable error shape;
test both the fixnum and bignum absurd-count paths.

**Follow-up recorded at fix time (PR #46's cap is the first of its kind):** the
same "user-controlled size → eager Rust allocation → uncatchable abort" class
exists unguarded in at least `make-vector` (`alloc_vector_fill` does
`vec![fill; len]` — `(make-vector (expt 2 40))` is 8 TiB), `make-string`,
`make-bytevector`, and `expt` (`BigInt::pow` with an exponent up to ~4×10^9).
The next item of this class should establish a shared allocation-size guard
(one knob, one error shape) rather than a second ad-hoc constant.

**Acceptance for group A:** all six fixed with regression tests at the
adaptation points; both chibi lanes stay 1226/1226; upstream SRFI suites stay
at their recorded totals.

## B — Continuation refactor follow-ups (PR #39)

The refactor is a clear win (sentinel-string encoding deleted, capture is an
O(1) Rc bump, escape path touches the heap zero times, real `guard` bug
fixed). These items close what it left behind before Q2 builds on it.

### B1 `[x]` (#47) HIGH — GC never traces `CpsContinuation.resume`
`crates/patina-core/src/heap/gc.rs:704-709` — `trace_continuation_children`
visits `body`, `env`, `dynamic_winds`, `captured_cont_env`; the new `resume`
field (`continuation.rs:63`) is absent, and it holds heap references
(consumer procedures, `after` thunks, cached promises, exception payloads).
Currently safe only because every construction site aliases the payload
through the traced `captured_cont_env` — an **undocumented invariant** with no
debug poison behind it; any cont-env pruning or out-of-env wrapper
construction breaks it silently. Verified latent (GC-stress repros survive
today).
**Fix sketch:** one line — trace `resume` in `trace_continuation_children` —
plus a comment stating the aliasing situation.

### B2 `[x]` (#47) MEDIUM — `ContValue::Captured` decode path contradicts the new design
`crates/patina-tree-walker/src/eval/cps_eval/continuation.rs:149-167` — the
`Captured` arm of `invoke_continuation_step` evaluates `k.body` with the
**caller's** cont_env and ignores `resume`/`captured_cont_env`; a
resume-bearing continuation invoked through it would evaluate the sentinel
`Halt(Var "__resume_value__")` body and die. Unreachable today (`Captured` is
never constructed), but it is exactly the constructor Q2's first-class
continuation work will reach for.
**Fix sketch:** route the arm through the same escape logic as
`cps_eval/mod.rs:304-321`, or replace it with an explicit
`unreachable!`-with-rationale until Q2 defines it.

### B3 `[x]` (#47) MEDIUM — handler-loss-on-re-entry divergence is claimed "tracked separately"; nothing tracks it
`crates/patina-tree-walker/src/eval/cps_eval/mod.rs:294-300` — the comment
documents that `exception_handlers`/`prompt_stack` are *reset*, not restored,
on continuation re-entry (a real tree-walker/VM behavioral divergence) and
says it is tracked separately. No entry exists in
`backend_divergence.rs`, `PRD/`, or `docs/`. This is precisely the
comment-only defect class Track Q §1 exists to eliminate.
**Fix sketch:** add an `assert_divergence` quarantine case (raising the
Track Q §7 count from 6) or fix the comment if the behavior is actually
identical — measure first.

### B4 `[x]` (#47) LOW — dead/stale remnants in the new core API
`crates/patina-core/src/cont_value.rs:249-276` — `wrapped_cont()` has zero
callers and its doc describes pre-refactor behavior ("bespoke serialization"
that this refactor deleted). Also: `Captured`'s `#[allow(dead_code)]` +
"will be used when serialization is implemented" comment is stale
(`cont_value.rs:185-188`); `capture_cont_bindings` carries two stacked doc
headers and is now an identity wrapper
(`cps_eval/continuation.rs:18-31`); the relocated tracing functions sit under
the `// Tests` section banner in `gc.rs` (`:932-1046`) and pub
`trace_exception_handler` is undocumented.
**Fix sketch:** delete `wrapped_cont`, fix the comments, move the banner.

**Acceptance for group B:** B1's trace landed with the GC differential lanes
green; `Captured` either functional or explicitly fenced; the B3 divergence
either quarantined or disproven; no doc comment in `cont_value.rs` describes
deleted behavior.

## C — Performance

Both C1 and C2 run directly against the recorded Track P profile (per-call
mallocs ≈ 17% of VM runtime). Validate per Track P practice: interleaved
main/branch/main runs, never a single run vs a stored baseline.

### C1 `[ ]` MEDIUM — bitwise primitives have no fixnum fast path
`crates/patina-primitives/src/primitives/bitwise.rs:22-62` — `int_arg`
promotes every fixnum argument via `BigInt::from` (heap-allocating) with a
`RefCell` borrow per argument; `(bitwise-and 12 10)` costs ≥ 2 mallocs. All
SRFI 143 "fast fixnum" bitwise ops (`fxand`, `fxior`, `fxxor`, `fxnot`,
`fxarithmetic-shift`, `fxbit-count`, …) alias these same primitives, so the
fixnum library allocates bignums on every call. The header comment documents
the all-BigInt approach as deliberate simplicity — reasonable to start, wrong
to keep.
**Fix sketch:** `as_fixnum()` fast path for and/ior/xor/not (+ small-count
shifts); i64 ops agree with infinite-precision two's complement within fixnum
range. Bignum promotion stays as the slow path.

### C2 `[ ]` MEDIUM — base `string-map`/`vector-map` family allocates per element
`lib/scheme/base/higher_order.scm:68-119` — the move from Rust to Scheme was
justified (the Rust higher-order frames drop captured continuations; fixed a
real SRFI 158 bug, removed a backend divergence), but each element now costs a
fresh closure + a `map`-built argument list + an `apply`, even in the dominant
single-sequence case, on four `(scheme base)` procedures.
**Fix sketch:** single-sequence direct-loop split
(`(if (null? (cdr seqs)) <direct loop> <n-ary loop>)`) — the same shape
chibi's `init-7.scm` uses for `map`.

### C3 `[ ]` MEDIUM — superseded continuation-broken Rust primitives still registered
`crates/patina-runtime/src/stdlib/internal_strings.rs:50-51`,
`internal_vectors.rs:39-40` — the four Rust `string-map`/`string-for-each`/
`vector-map`/`vector-for-each` primitives that C2's Scheme rewrite exists to
replace remain registered and exported. `lib/scheme/base.sld` imports the
internal libs wholesale and relies on the included Scheme defines shadowing
them (a library-body redefinition of an imported binding — an R7RS 5.6.1
error Patina happens to tolerate), and `(import (patina internal strings))`
still hands out the known-broken implementations. Two live implementations of
the same four names, one defective. Adjacent to the Track L §6
registry/import-set issue — coordinate, don't duplicate.
**Fix sketch:** delete the Rust implementations and their exports (or
un-export them from the internal library builders); the Scheme versions are
the only ones left standing.

**Acceptance for group C:** C1/C2 validated by interleaved benchmark runs with
no chibi-suite regression; after C3, `(import (patina internal strings))`
no longer exposes a broken `string-map`, and `(scheme base)` no longer
shadows an import.

## D — Test-infrastructure hardening (PRs #42/#43)

The parametrized harness, quarantine mechanism, and script consolidation are
well built (backend-naming failure messages, self-retiring `assert_divergence`
with mandatory tracking pointers, framework-derived totals, crash-mid-suite →
explicit failure). The shared weakness: **counts and error classes are
trusted, not pinned.**

### D1 `[x]` (#48) MEDIUM — no floor on the chibi-suite total
`scripts/run_chibi_tests.sh:197-199` exits 0 whenever failures = 0 and
errors = 0, regardless of how many tests ran; the CI step label
(`.github/workflows/ci.yml:47`) promises "must be 1226/1226" but nothing
enforces the 1226. Concretely reachable: the bundled `(chibi test)` honors
`TEST_FILTER`/`TEST_GROUP_FILTER`/`TEST_GROUP_REMOVE` from the environment
(`lib/chibi/test.scm:905-954`), and a truncated `r7rs-tests.scm` or a
skip-inducing framework change shrinks the total silently.
**Fix sketch:** an `EXPECTED_TOTAL` variable checked against the framework's
grand total, updated deliberately when the suite grows.

### D2 `[x]` (#48) MEDIUM — upstream SRFI suites: zero-test runs pass; tree-walker-only and doesn't say so
`crates/patina-tests/tests/upstream_srfi_suites.rs` — only the failure count
is asserted, never the assertions-run total, so an env-var filter or a
framework change that skips everything is green (`:52-72`); the README's
per-suite counts are prose, not checks. The suites also run tree-walker only
(`:60-61`) — the concrete blocker is that `VmBackend` exposes no public way to
add a library search path (`LibraryRegistry::add_search_path` exists;
`patina-vm/src/backend.rs` reads registry paths) — and unlike
`gc_tree_walker.rs`/`gc_vm.rs`, the module doc never states the
single-backend scope, so it reads as full coverage.
**Fix sketch:** assert a per-suite minimum assertions-run total (chibi test
tracks it); either add the search-path API and run both backends, or state
the scope in the module doc. Optional: split the six suites into separate
`#[test]`s so one load failure doesn't hide the rest.

### D3 `[x]` (#49) MEDIUM — the error-class dimension is unchecked, and the trade-off is unrecorded
`crates/patina-tests/tests/common/mod.rs:226-241` — `assert_eval_error` and
`eval_program` deliberately don't compare error text between backends, so
"both backends fail for *different reasons*" is invisible; in
`assert_divergence` (`:198-211`), the broken backend's failure *mode* changing
(e.g. undefined-variable → arity error) also passes silently — any `Err`
satisfies the check. Q1's own bar is "value *and* error class." Plausibly a
deliberate anti-brittleness choice, but nothing records it.
**Fix sketch:** compare a coarse error *class* (not text) between backends —
even a two-bucket eval-error/internal-error split catches mode drift — or
document in `common/mod.rs` that the dimension is deliberately unchecked and
why.

### D4 `[x]` (#48) MEDIUM — the tree-walker chibi lane is not gated in CI
`.github/workflows/ci.yml:38-48` — CI's chibi gate runs the VM backend only;
`run_chibi_tests_tree_walker.sh` is never invoked (pre-existing at the
baseline, unchanged by this work; noted here because Q1's remaining items
track the report-diff, not this gap). The GC differential jobs run the
tree-walker but only self-compare GC modes. Partially mitigated by the
parametrized 1,148-test suite; chibi-suite-only tree-walker regressions still
pass CI.
**Fix sketch:** one CI step running the `--tree-walker` lane (it shares the
release build with the existing step), with D1's total floor.

### D5 `[x]` (#48) MEDIUM — the `[profile.test]` opt-level win exists only in out-of-repo memory
No `[profile.*]` section exists in any workspace `Cargo.toml`, and no PRD
mentions it; the measured ~6× test-bootstrap improvement from Track P
exploration survives only in conversation memory and is at risk of being
lost.
**Fix sketch:** land `[profile.test] opt-level = 1` (or the measured best) in
the workspace `Cargo.toml` with a comment recording the measurement, and
re-verify the suite wall-clock before/after.

**Acceptance for group D:** a filtered/truncated chibi run fails the script; a
zero-assertion SRFI suite run fails; both backends' chibi lanes are CI-gated;
error-class policy is either implemented or documented where the code makes
the choice.

## E — Provenance and documentation debt

### E1 `[x]` (#50) MEDIUM — SRFI 132's "unmodified" claim is false, and the edits are unmarked
`lib/srfi/132.sld:3-9` says "The reference implementation, unmodified… Each
file carries its own notice; none has been removed." Three of eleven files
carry unmarked local edits: `select.scm` (the A1 RNG substitution +
`r7rs-vector-copy!` renames), `vector-util.scm` (rewritten to alias native
`vector-copy`, originals parked behind `#;`), `vmsort.scm` (two renames).
`select.scm` also carries no notice at all (Clinger's 2016 addition; upstream
has none either).
**Fix sketch:** correct the `.sld` header, add a `;; PATINA LOCAL EDIT:`
marker at each edit site (per the rule at the top of this doc), and note
`select.scm`'s provenance explicitly.

### E2 `[x]` (#50) MEDIUM — `lib/chibi/diff` and `lib/chibi/optional` have zero provenance
Neither file has an in-file header (upstream relies on chibi's repo-level BSD
license), and the move out of `compat/vendor/` deleted their `MANIFEST.json`
entries (upstream URL, version 0.9.0, tarball sha256). No record anywhere in
the repo says where this code came from. `lib/chibi/test.scm` and
`term/ansi.scm` are fine (in-file BSD headers); SRFI 132 and 151 document
themselves in their `.sld`s.
**Fix sketch:** add a short provenance header to each file (upstream repo,
version, license pointer), or restore manifest entries in a
`lib/chibi/PROVENANCE.md`-style record — one home, per Q6's rule.

### E3 `[x]` (#50) LOW — `(chibi test)`'s "verbatim" claim is unverifiable, and its export list is unguarded
`scheme_tests/upstream/README.md:103` says the bundled `(chibi test)` is
"verbatim from upstream", but `lib/chibi/test.scm:9-14` contains a local
SRFI-1 `any` shim, the copy is the 0.9.x snowball vintage (© 2010-2020, vs
upstream head's 2010-2025), and no upstream commit/tarball pin is recorded
(it went with the deleted MANIFEST entry). The deleted
`bundled_vs_vendored.rs` also took the last export-list guard against
upstream with it. Footnote: the vendored `string-search` has an inherited
upstream off-by-one (last-position matches missed) affecting only
`TEST_FILTER` matching — an upstream-sync candidate, not a local defect.
**Fix sketch:** record the pinned snowball version + the one local shim in
the README (or the E2 provenance record); optionally re-add a small
export-list check against the recorded upstream list.

**Acceptance for group E:** every file under `lib/chibi/` and `lib/srfi/132/`
has a discoverable origin record; no header claims "unmodified"/"verbatim"
where a diff against upstream says otherwise.
